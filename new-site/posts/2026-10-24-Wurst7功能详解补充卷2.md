### F.3 隐私相关事实小结

- 唯一的"持续"出站是 Plausible 统计，可通过 `.wurst/analytics.json` 关闭，dev/gametest 环境只打日志不发送（`PlausibleAnalytics.java:140-144`）。
- 两个功能会把**用户内容发给第三方**：AutoComplete（聊天上下文 → OpenAI 或自定义端点）、ChatTranslator（消息原文 → Google）——均需用户主动启用对应功能。
- alt 列表本地加密存储（RSA-1024 包 AES-128-CFB8，密钥在 `~/.Wurst encryption/`，见主报告 4.4），不上传。
- `mixin/ServerNameResolverMixin.java` 拦截地址解析处理 Mojang 影子封禁重定向（入站行为修改，非出站）。

## H. 渲染基础设施

ESP/X-Ray/Search/寻路可视化共用的底层渲染栈，分五层：RegionPos（坐标基准）→ 偏移应用（RenderUtils）→ 图层定义（WurstRenderLayers）→ 顶点缓冲（WurstBufferSource / EasyVertexBuffer）→ 绘制原语（RenderUtils）。

### H.1 RegionPos — 512 格区域坐标（`util/RegionPos.java`）

`record RegionPos(int x, int z)`，`of()` 把坐标对齐到 **512 格网格**（`pos.getX() >> 9 << 9`，:16-19；512 = 2⁹，即 32×32 区块一片）。提供 `negate()` 与 `toVec3d()`（:26-34）。

**为什么需要它**：世界坐标可达 ±3000 万，float32 顶点在远离原点处精度崩坏（视觉抖动）。`[推断]` 标准解法是"减去一个大基准量再渲染"，Wurst 选 512 格网格作为基准：见 H.2 的区域偏移。选网格而非"相机所在区块"的原因见 H.2 末段。

### H.2 两种渲染偏移（`util/RenderUtils.java:40-62`）

```java
// 区域偏移：平移 (region − cameraPos)，:51-56
public static void applyRegionalRenderOffset(PoseStack matrixStack, RegionPos region) {
    Vec3 offset = region.toVec3d().subtract(getCameraPos());
    matrixStack.translate(offset.x, offset.y, offset.z);
}
// 相机偏移：直接平移 −cameraPos，:58-62
public static void applyRenderOffset(PoseStack matrixStack) { ... }
```

两种模式的分工：

| 模式 | 顶点坐标系 | 适用场景 | 代价 |
|---|---|---|---|
| **相机偏移** `getCameraPos().reverse()` | 世界坐标 − 相机位置（顶点**每帧**按相机重算） | `drawLine/drawTracer/drawSolidBox/drawOutlinedBox/drawCrossBox` 等即时绘制原语（:123,142,267,356,470 等——每个原语内部先 `box.move(getCameraPos().reverse())` 再编码） | 每帧重编码顶点 |
| **区域偏移** `applyRegionalRenderOffset` | 世界坐标 − 512 格区域原点（顶点**一次编译、跨帧复用**） | Search 的 VBO（`SearchHack.java` 的 `setBufferFromTask` 上传后按相机 region 偏移绘制）、NewChunks 渲染器（相机跨 region 时才强制重建，`NewChunksHack.java:296-306`）、`PathFinder.renderPath` 的路径箭头（`ai/PathFinder.java:554-556`） | 只在跨 region 边界时重建缓冲 |

`[推断]` 这就是区域选 512 格整数网格的原因：静态缓冲只在玩家跨过 region 边界时失效一次，其余时间零重建开销；若以相机区块为基准，每跨一个区块（16 格）就要重建。

### H.3 WurstBufferSource — 即时绘制批次（`util/WurstBufferSource.java`）

类注释（:24-26）："Simple wrapper around `StagedVertexBuffer` to replace Minecraft's `MultiBufferSource` **which was removed in 26.2-snapshot-5**"——上游 API 移除后 Wurst 自建替代。

- `getBuffer(RenderType)`（:35-49）：同层连续绘制**合并**（`canConsolidateConsecutiveGeometry()` 时复用上一个 Draw），否则 `stagedBuffer.appendDraw` 新开一批；
- `uploadAndDraw()`（:51-82）：上传 → 在主渲染目标上开 `RenderPass`（RenderPearl GPU API，即 Vibrant Visuals 时代的命令编码器模型，:62-66）→ `bindDefaultUniforms` → 逐 Draw 调 `type.prepare().drawFromBuffer` → finally 清空列表并 close。**每次调用完整走一遍上传-绘制-释放**，是一次性几何（每帧 ESP 框）的路径。

### H.4 EasyVertexBuffer — 静态顶点缓冲（`util/EasyVertexBuffer.java`）

javadoc（:37-40）："An abstraction of Minecraft 1.21.5's new `GpuBuffer` system that makes working with it **as easy as `VertexBuffer` was**"——新 GPU 缓冲 API 的简化封装。

- `createAndUpload(drawMode, format, callback)`（:50-67）：`BufferBuilder` 收集顶点 → 一次上传为 `GpuBuffer`（`USAGE_VERTEX|COPY_DST`，:76-78）；空几何返回空对象不报错；
- `draw(matrixStack, layer, rgba)`（:116-151）：压入模型视图矩阵 → `getDynamicUniforms().writeTransform`（颜色以 uniform 传入，同一缓冲可用不同颜色重绘）→ 开 RenderPass → `drawIndexed`；
- 与 H.3 的关系：EasyVertexBuffer = **持久**缓冲（上传一次画多帧），WurstBufferSource = **一次性**批次（当帧上传当帧释放）。Search 用前者（结果不变就重用 VBO），ESP 框用后者（目标每 tick 变）。

### H.5 WurstRenderLayers — 自定义图层（`WurstRenderLayers.java`）

5 个图层，全部基于 `WurstShaderPipelines` 自定义管线：

| 图层 | 定义 | 用途 |
|---|---|---|
| `LINES` | 类似原版 lines 但**线宽 2**（:17-25） | 深度测试开启的线框 |
| `ESP_LINES` | LINES + **无深度测试**（:27-33） | 透视 ESP 线 |
| `QUADS` | 类似 debug quads 但**开面剔除 + sortOnUpload**（:35-40） | 实心盒（深度测试） |
| `ESP_QUADS` | QUADS + 无深度测试（:42-47） | 透视实心盒 |
| `ESP_QUADS_NO_CULLING` | 无深度测试且**无剔除** + 光照图（:49-55） | 双面实心 |

`getLines(boolean)`/`getQuads(boolean)` 是按 `depthTest` 二选一的工厂（:63-75）——每个绘制原语的 `depthTest` 参数直接落到这两个工厂上。线宽 2 不在渲染状态里而在**每个顶点**上（`setLineWidth(2)`，`RenderUtils.java:197` 等）。

### H.6 值得注意的实现细节

- **穿屏线段补丁**（`RenderUtils.java:199-210`）：`drawLine` 检测线段是否穿过屏幕平面（点到相机平面的投影参数 `t ∈ (0, length)`），命中时在最近点**补一对重合顶点**——源码注释 "This works around a bug in Minecraft's line shader"。tracer/长线必经此路径，否则线在穿屏处消失或变向。
- **Tracer 起点**（:129-132）：`getTracerOrigin = 相机朝向向量 × 10`——tracer 不从相机原点画，而从视线方向 10 格处的点出发。`[推断]` 该点近似"屏幕中心前方"，避免线从画面正中穿出、也避免与玩家模型自相交。
- **2D GUI 绘制层**（:714-936）：`drawItem`（HUD 物品图标）、`fill2D/drawLine2D/drawBorder2D` 等——javadoc 反复强调与原版 `GuiGraphicsExtractor` 的差异是"**浮点坐标** + **1 实际像素**宽（而非 1 缩放像素）"（:828-831,856-857）：先乘 GUI scale 再反向 scale 矩阵，绕过原版取整。`drawLine2D` 用"平移+旋转+画水平线"实现任意斜线（:832-850）。
- **三角形绘制**（:796-824）：`fillTriangle2D` 注释原文 "Pretends to render the given vertices in TRIANGLES draw mode by squeezing a bunch of quads into triangle shapes. ...**blame Vibrant Visuals**"——新渲染管线下三角形模式不可用，用退化四边形（两点重合）拼三角形。
- **drawNode/drawArrow**（:622-712）：寻路可视化原语——node 是 12 线段的星形标记（中/上/下三部分），arrow 是主线 + 经 `atan2` 双轴旋转定位的箭头锥（头锥 10 条短线）；`drawArrow(BlockPos, BlockPos, RegionPos)` 变体按 region 原点平移后绘制（:660-667），与 `PathFinder.renderPath` 配套。
- **彩虹色**（:96-106）：三轴相位差 1/3 周期的正弦，2 秒一轮——RainbowUi/雷达等共享。
